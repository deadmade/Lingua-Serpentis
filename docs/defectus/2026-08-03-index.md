# Lingua Serpentis — Defect Register

Opened 2026-08-03 by the conformance and robustness suite
(`docs/superpowers/specs/2026-08-03-conformance-and-robustness-suite-design.md`).

**Nothing here is fixed.** Each defect has a fixture under
`conformance/defectus/` pinning today's behaviour so `cargo test` stays green.
Fixing a defect makes its fixture fail — that failure is the acceptance
criterion. Move the fixture to the right category with the corrected
expectation as part of the fix.

Defects that need a subprocess, a filesystem manipulation, or that have no
executable repro at all are not fixture-shaped. Their entries name the test that
covers them instead. Those test files (`crates/lingua-serpentis/tests/cli.rs`,
`robustness.rs`, `generative.rs`) arrive with Tasks 9-12 and do not exist yet.

Every observation below was reproduced against `target/debug/lingua-serpentis`
on 2026-08-03 and every `file:line` was read at the cited location on the same
day. Where this register disagreed with the design's §8.1 table, the register
was the corrected reading and §8.1 has since been brought into line — the
changes are listed in **Appendix A**.

D-01 through D-21 are §8.1's confirmed defects. **D-22 is not in §8.1** — it
surfaced while reproducing the others and was triaged in, which is the process
§8.1 describes for further candidates. **D-23** surfaced the same way, while
writing Task 10's curated pathologies. **Appendix B** is the triage log, and
records the one finding that was examined and ruled *not* a defect.

### D-01 · Nulla analysis reditus — the type system is unsound

- **Severity:** high — a checker-approved program produces a value of the wrong type
- **Repro:** `conformance/defectus/D-01-reditus-omissus/`
- **Observed:** `munus nomen reddit voc { si (falsus) { redde "a"; } }` called from
  `initium` prints `nullus` on stdout, empty stderr, exit 0 — a declared-`voc`
  call yielded an `Int`.
- **Expected:** a checker error naming the missing return.
- **Cause:** `interp.rs:168` ends every call body with `Ok(Value::Int(Roman::zero()))`
  regardless of the declared return type; `checker.rs:412` only type-checks the
  `redde` statements actually written and never asks whether one is reachable on
  every path.
- **Note:** this is what promotes the "defensive" interpreter messages from
  unreachable to reachable. Both were confirmed by hand:
  `scribe(nomen() + "b")` gives
  `Error in 'principale.liss', linea 8: operatio binaria invalida`, and
  `si (vera())` on a `reddit veritas` function with no reachable `redde` gives
  `Error in 'principale.liss', linea 8: condicio non est veritas`.
  `comparatio invalida` (`interp.rs:358`) and `subscriptio invalida`
  (`interp.rs:136`) are reachable by the same route.
  Any fix must special-case `initium`, whose fall-through the packages design
  licenses deliberately and which `interp.rs:609::falling_off_initium_exits_zero`
  pins as correct.

### D-02 · `expectatum: Semicolon` — a Rust type name in a Latin diagnostic

- **Severity:** medium — user-facing text is coupled to a private Rust enum
- **Repro:** `conformance/errores/expectatum-semicolon/`
- **Observed:** a missing `;` gives
  `Error in 'principale.liss', linea 3: expectatum: Semicolon`, exit 1.
- **Expected:** the Latin name of the missing token, e.g. `expectatum: ';'`.
- **Cause:** `parser.rs:28` — `Err(self.err(&format!("expectatum: {:?}", kind)))`
  formats a `TokenKind` with `Debug`. There are 29 `self.eat(...)` call sites
  reaching it, over exactly **7** distinct variants: `Assign`, `LBrace`,
  `LParen`, `RBrace`, `RBracket`, `RParen`, `Semicolon`. Renaming any one of
  those variants silently changes user-facing text.
- **Note:** the fixture also pins that the reported line is 3, not 2 — the
  parser reports at the token *following* the missing semicolon.

### D-03 · Line numbers are wrong after a multi-line string

- **Severity:** high — every diagnostic and warning after a multi-line string
  points at the wrong source line
- **Repro:** `conformance/defectus/D-03-linea-post-chordam/`
- **Observed:** a string literal spanning source lines 2-3, then an undefined
  variable on source line 5, gives
  `Error in 'principale.liss', linea 4: variabilis ignota: 'ignota'`, exit 1.
- **Expected:** the same message with `linea 5`. The drift is one line per
  embedded newline, and is unbounded.
- **Cause:** `lexer.rs:46` — the string body is scanned with
  `while i < chars.len() && chars[i] != '"' { i += 1; }`, which walks over `\n`
  without incrementing `line`. Every token emitted afterwards carries the
  understated number, so `Monitum in ..., linea N` drifts identically.

### D-04 · Unbounded recursion aborts the process

- **Severity:** high — the failure is outside the error model entirely; an
  embedder cannot survive it
- **Repro:** `munus recurre capit (ni n) reddit ni { redde recurre(n + °I); }`
  called from `initium`. Not fixture-shaped: `SIGABRT` kills the test process
  and `catch_unwind` does not catch it, so this needs a subprocess.
- **Covered by:** `crates/lingua-serpentis/tests/cli.rs` (as an `#[ignore]`d
  test) and the `robustness.rs` `no abort` invariant with a D-04 allowlist entry.
- **Observed:** stdout empty; stderr
  `\nthread 'main' (<pid>) has overflowed its stack\nfatal runtime error: stack overflow, aborting`;
  exit **134** (128 + SIGABRT).
- **Expected:** a Latin diagnostic and exit 1, or a documented recursion limit.
- **Cause:** `interp.rs:142` — `Interp::call` recurses through
  `exec` → `eval` (`interp.rs:83`, the `Expr::Call` arm) → `call` with no depth
  counter and no growable stack.

### D-05 · Deep expression nesting aborts in the parser

- **Severity:** medium — a malformed or machine-generated source file aborts
  the process instead of producing a diagnostic
- **Repro:** `ni x = ((((…°I…))));` with 2000 or more nested parentheses. Not
  fixture-shaped for the same reason as D-04.
- **Covered by:** the `robustness.rs` nesting-depth pathology sweep with a D-05
  allowlist entry against the `no abort` invariant.
- **Observed:** measured in the debug build on 2026-08-03: 1000 nested
  parentheses → exit 0, clean; **2000** → exit 134 with
  `fatal runtime error: stack overflow, aborting`. 4000, 8000 and 20000 behave
  the same as 2000.
- **Expected:** a Latin diagnostic and exit 1, or a documented nesting limit.
- **Cause:** `parser.rs:143` — `primary`'s `LParen` arm calls `self.expr()`, so
  the whole recursive-descent chain `expr → or_expr → … → unary → primary`
  re-enters once per parenthesis, with no depth counter.
- **Note:** the design's §8.1 estimate of "~20k nested parens" is an order of
  magnitude too generous for the debug build; see Appendix A.

### D-06 · A broken pipe panics

- **Severity:** medium — the most ordinary shell idiom (`prog | head`) produces
  a Rust panic message and a non-standard exit status
- **Repro:** a program printing many lines, piped into `head -1`. Not
  fixture-shaped: the library never touches a pipe, only `main.rs` does.
- **Covered by:** `crates/lingua-serpentis/tests/cli.rs` (as an `#[ignore]`d
  test) and the `robustness.rs` `no panic` invariant with a D-06 allowlist entry.
- **Observed:** one line of correct output, then on stderr
  `thread 'main' (<pid>) panicked at …/std/src/io/stdio.rs:1166:9:` /
  `failed printing to stdout: Broken pipe (os error 32)` /
  `note: run with RUST_BACKTRACE=1 …`; exit **101**.
- **Expected:** silent termination on `EPIPE`, the way every Unix tool behaves.
- **Cause:** `main.rs:9` — `print!("{}", r.stdout)` panics on a write error
  because Rust's runtime sets `SIGPIPE` to `SIG_IGN`. `main.rs:8`'s `eprint!`
  has the same exposure on stderr.

### D-07 · `abrumpe` extra iterationem tacite ignoratur

- **Severity:** medium — silently wrong behaviour, no diagnostic
- **Repro:** `conformance/defectus/D-07-abrumpe-extra-iterationem/`
- **Observed:** `scribe(°I); abrumpe; scribe(°II);` directly in `initium` prints
  `I` then `II`; stderr empty; exit 0. `continua` in the same position is
  identical.
- **Expected:** an error naming `abrumpe` outside a loop.
- **Cause:** `checker.rs:449` — `StmtKind::Break | StmtKind::Continue => Ok(())`,
  with no loop-depth tracking anywhere in the checker; `interp.rs:225` yields
  `Flow::Break`, and the function-body loop at `interp.rs:166` matches only
  `Flow::Return`, so the `Break` is dropped on the floor.

### D-08 · A runtime error discards everything already printed

- **Severity:** high — output the program provably produced is thrown away
- **Repro:** `conformance/defectus/D-08-emissio-perdita/`
- **Observed:** `scribe("ante")` followed by a division by zero gives **empty**
  stdout, stderr `Error in 'principale.liss', linea 4: divisio per nullum`,
  exit 1.
- **Expected:** stdout `ante`, then the error on stderr.
- **Cause:** `interp.rs` accumulates `scribe` output in `Interp::out`;
  `execute_program` (`interp.rs:390`) returns it only in the `Ok` arm, and
  `run_loaded`'s `?` at `lib.rs:44` discards it. `render` (`lib.rs:121`) then
  emits an empty stdout for any `Err`.

### D-09 · Any error discards all Latinity warnings

- **Severity:** medium — a diagnostic the linter produced is computed and thrown
  away, so a program with two problems only ever reports one
- **Repro:** `conformance/defectus/D-09-monita-perdita/`
- **Observed:** a program with the non-Latin name `counter` **and** a division by
  zero gives stderr containing only
  `Error in 'principale.liss', linea 4: divisio per nullum`, exit 1. Remove the
  division and the same program emits
  `Monitum in 'principale.liss', linea 2: nomen 'counter' fortasse non Latinum est`
  — so the warning exists and is discarded.
- **Expected:** the `Monitum` line, then the error.
- **Cause:** `lib.rs:43` computes `warnings`; `run_loaded` returns them only on
  the `Ok` arm at `lib.rs:45`. The `?` on `lib.rs:44` (interpreter) and the `?`
  on `lib.rs:42` (checker) both drop them.

### D-10 · The exit status is silently truncated

- **Severity:** low — Unix-correct but undiagnosed; a program's own status can
  become 0
- **Repro:** `munus initium reddit ni { redde °CCC; }`. Not fixture-shaped: the
  library's `run_with_warnings` discards the `u8` (`lib.rs:88`), so only a
  subprocess observes the real status.
- **Covered by:** `crates/lingua-serpentis/tests/cli.rs`.
- **Observed:** `redde °CCC` (300) → exit **44**; `redde nullus - °I` (-1) →
  exit **255**; `redde °CCLVI` (256) → exit **0**. No warning in any case.
- **Expected:** at minimum a `Monitum` when the returned `ni` does not fit in
  0..=255.
- **Cause:** `interp.rs:381` — `exit_status` reduces mod 256 and shifts a
  negative remainder up by one modulus. The behaviour is deliberate and
  documented in the doc comment above it; what is missing is any signal to the
  user that it happened.

### D-11 · Two English diagnostics in `main.rs`

- **Severity:** low — but it is the one rule the language has: every message the
  user sees is Latin
- **Repro:** `lingua-serpentis notae.txt` and `lingua-serpentis absens.liss`.
  Not fixture-shaped: both sites are in `main.rs`, which the in-process runner
  never enters.
- **Covered by:** `crates/lingua-serpentis/tests/cli.rs` and the
  `robustness.rs` `Latin only` invariant with a D-11 allowlist entry.
- **Observed:**
  - a path not ending in `.liss` → `Error: file must have .liss extension`, exit 1;
  - a missing file → `Error reading file: No such file or directory (os error 2)`,
    exit 1.
  Both sit one line below the correctly-Latin
  `Usus: lingua-serpentis <via.liss | directorium>` (`main.rs:16`).
- **Expected:** Latin, in the `Error: …` shape the rest of the language uses.
- **Cause:** `main.rs:24` and `main.rs:29`.
- **Note:** the second message is also *wrong* for a directory argument that
  does not exist. A nonexistent `directorium/` fails `is_dir()`, falls through
  the extension check and reports `Error: file must have .liss extension` — the
  first message, misapplied. A nonexistent `directorium.liss/` reports
  `Error reading file: …` — the second message, calling a directory a file.
  The design's §8.1 attributes the misfire only to the second; both misfire.

### D-12 · Arabic numerals in a user-visible message

- **Severity:** low — the only user-visible Arabic number left in the language
- **Repro:** `conformance/errores/index-extra-fines/`
- **Observed:** `xs[°X]` on a two-element list gives
  `Error in 'principale.liss', linea 3: index extra fines: X (longitudo 2)`,
  exit 1. The index is rendered through `Roman::display()`; the length is a
  bare `usize`.
- **Expected:** `(longitudo II)`.
- **Cause:** `interp.rs:131` and `interp.rs:207` — both build
  `format!("index extra fines: {} (longitudo {})", idx.display(), items.len())`.
  Two sites, identical text; a fix must change both.
- **Note:** roman-native-integers §1 promises "no Arabic number anywhere a user
  can see". This is the counterexample.

### D-13 · Roman numeral form is never validated

- **Severity:** medium — the language's central literal accepts non-numerals
- **Repro:** `conformance/defectus/D-13-numerus-non-canonicus/`
- **Observed:** `scribe(°IIX + °VV + °IM);` prints `MXIX`, exit 0. Individually:
  `°IIX` → `X` (10), `°VV` → `X` (10), `°IM` → `CMXCIX` (999).
- **Expected:** `numerus Romanus invalidus` for each.
- **Cause:** `roman.rs:204` — `convert_single`'s loop applies the subtractive
  rule positionally (`if next_bigger { total.sub } else { total.add }`) and
  accepts any string over `I V X L C D M`. Nothing constrains repetition counts,
  nothing restricts which subtractive pairs are legal, and the result is never
  re-rendered and compared against the input.
- **Note:** numeral-form validation is a language change, listed under the
  conformance suite design's §2 Non-Goals. This entry records the hole; it does
  not schedule the fix.

### D-14 · `°X/°II` lexes as one numeral; whitespace is load-bearing

- **Severity:** medium — the same expression means two different things
  depending on a space, with no diagnostic explaining why
- **Repro:** `conformance/defectus/D-14-numerus-sine-spatio/`
- **Observed:** `scribe(°X/°II);` gives
  `Error in 'principale.liss', linea 2: numerus Romanus invalidus: 'X/'`, exit 1.
  Written `scribe(°X / °II);` the identical program prints `V` and exits 0.
  The same trap exists for `.`: `°V.summa` gives `numerus Romanus vacuus`
  (`roman.rs:193`).
- **Expected:** either `°X/°II` lexes as a division, or the diagnostic says that
  `/` was consumed as part of the numeral.
- **Cause:** `lexer.rs:85` — `is_roman_body` accepts `'.' | ':' | '/'` because
  fraction literals are written `°V:I/II` and thousands-multiplication as
  `°XXX.M`. The `°` arm at `lexer.rs:34` then consumes greedily to the first
  non-body character, with no backtracking when the result fails to parse.

### D-15 · Arabic digits get the lexer's catch-all, with no hint

- **Severity:** low — but it is the likeliest first mistake a newcomer makes in
  a Roman-numeral language
- **Repro:** `conformance/errores/signum-ignotum/`
- **Observed:** `ni x = 5;` gives
  `Error in 'principale.liss', linea 2: signum ignotum: '5'`, exit 1.
- **Expected:** a message that says a numeral is written `°V`.
- **Cause:** `lexer.rs:73` — the final `_ =>` arm of `tokenize`'s match returns
  `signum ignotum: '{c}'` for any unrecognized character. `'0'..='9'` is not
  special-cased anywhere ahead of it.

### D-16 · Duplicate parameter names are accepted; the last binding wins

- **Severity:** medium — silently wrong behaviour, and an argument becomes
  unreachable
- **Repro:** `conformance/defectus/D-16-parametri-gemini/`
- **Observed:** `munus f capit (ni a, voc a) reddit voc { redde a; }` called as
  `f(°I, "secunda")` prints `secunda`, stderr empty, exit 0. The body sees the
  `voc`; the `ni` argument cannot be named at all.
- **Expected:** an error naming the duplicated parameter.
- **Cause:** three last-wins sites, all of which must change together. The line
  cited for each is the statement that must change, not the enclosing function:
  - `parser.rs:305` — `params.push((ty, pname))`, with no uniqueness check.
  - `checker.rs:39` — the `insert` inside `declare`, reached once per parameter
    from `checker.rs:404`.
  - `interp.rs:154` — `frame.insert(pname.clone(), v)`, inside the loop opened
    at `interp.rs:153`.

### D-17 · A stray hidden directory containing a `.liss` kills the program

- **Severity:** medium — running a program folder that happens to be a git
  checkout can fail for a reason that has nothing to do with the program
- **Repro:** a program folder containing `.git/x.liss`. Not fixture-shaped: the
  corpus cannot carry a `.git/` directory, so this needs a filesystem
  manipulation at test time.
- **Covered by:** `crates/lingua-serpentis/tests/cli.rs`.
- **Observed:** stdout empty, stderr
  `Error: nomen fasciculi '.git' non validum est`, exit 1 — even though
  `principale.liss` beside it is a perfectly good program.
- **Expected:** hidden directories skipped, as every other tool that walks a
  source tree does.
- **Cause:** `program.rs:81` — `collect_liss` recurses into *every* directory
  entry with no `name.starts_with('.')` filter; `assemble` then rejects `.git`
  as a package name at `program.rs:42`, because `.git` does not lex as a single
  identifier.

### D-18 · `examples/calc.liss` warns on `summare`

- **Severity:** low — but it is a shipped example that does not lint clean, and
  a design decision that was deferred and then never taken
- **Repro:** `conformance/currunt/exemplum-calc/` (which pins the warning)
- **Observed:** `lingua-serpentis examples/calc.liss` exits 0 with stderr
  `Monitum in linea 1: nomen 'summare' fortasse non Latinum est`.
- **Expected:** per the decision the design deferred — either a supplemental
  word list that accepts `summare`, or a rename of the example.
- **Cause:** `docs/superpowers/specs/2026-07-19-latin-identifier-checker-design.md`
  §12 lists as an open question "*Whether a handful of common programmer-Latin
  infinitives used as function names (e.g. `summare`) are present in Whitaker or
  need a tiny supplemental list (verify during impl; add a small
  `data/supplement.txt` only if a real example fails).*" A real example does
  fail — this one — and `crates/latinitas/data/supplement.txt` does not exist.
  The warning itself is emitted at `latinity.rs:47`.
- **Note:** nothing noticed because no test looked. `tests/programs.rs:23`'s
  `calc_example_still_runs` calls `run()`, which discards warnings
  (`lib.rs:93`). The same design's §10 carries a parenthetical prediction that
  `calc.liss` "should lint cleanly"; reality contradicts it, which is exactly
  the trigger §12 named.
- **Not a defect, deliberately:** `examples/praecisio.liss` warns on
  `tertia_brevis` and `tertia_longa`. §9.1 of the same design lists "a name with
  a digit/underscore" as a specified **negative** for `latinitas::is_latin`.
  That is the checker working. It gets no defect ID.

### D-19 · 62 unit tests run against the laxer legacy API

- **Severity:** medium — the largest block of tests in the workspace certifies a
  language the compiler does not implement
- **Repro:** none — this is a property of the test suite, not of a program.
- **Covered by:** this register only. The conformance suite design's §2
  explicitly declines to resolve it ("No rewrite of the existing 242 tests").
- **Observed:** counted on 2026-08-03 by splitting each file on `#[test]`:
  `parser.rs` 17 of 33, `checker.rs` 29 of 40, `interp.rs` 16 of 30 — **62** of
  103 — drive `parser::parse` / `checker::check` / `interp::execute` through the
  test helpers `parse_all` / `parse_err` (`parser.rs:465`, `parser.rs:469`),
  `check_src` (`checker.rs:640`) and `run` (`interp.rs:434`). Typical bodies are
  `check_src("ni x = °V; x = x + °I; scribe(x);")` and
  `run("scribe(°V + °III * °II);")` — neither is a legal program.
- **Expected:** the unit tests exercise the same language the binary does, or
  the legacy entry points are removed.
- **Cause:** three parallel entry points that are strictly laxer than the
  program pipeline:
  - `parser::parse` (`parser.rs:409`) loops `statement()` over every token, so
    top-level statements are legal; `parse_file` (`parser.rs:420`) allows only
    `affer` lines followed by `munus` declarations.
  - `checker::check` (`checker.rs:519`) registers functions with a plain
    `insert` and has **no** duplicate check; `collect_sigs` (`checker.rs:553`)
    raises `functio '{}' bis definita`. `check` also has no `initium`
    requirement; `check_program` (`checker.rs:599`) raises
    `munus 'initium' in programmate non inventum`.
  - `interp::execute` (`interp.rs:363`) executes top-level statements directly
    and never looks for `initium`; `execute_program` (`interp.rs:390`) calls it
    as the entry point.
- **Note:** the design's §8.1 says "~50"; the measured figure is 62. See
  Appendix A.

### D-20 · `x = x * x` in a loop runs forever

- **Severity:** low — no wrong answer, but no diagnostic and no bound either
- **Repro:** `ni x = °II; indem (i minor_est °C) { x = x * x; i = i + °I; }`.
  Not fixture-shaped: the fixture runner has no timeout, so this would hang
  `cargo test`.
- **Covered by:** the `robustness.rs` `terminates` invariant (per-input timeout)
  with a D-20 allowlist entry.
- **Observed:** killed by `timeout 20` — exit 124, no output, no diagnostic. One
  hundred squarings of 2 is 2^(2^100), so this is not a slow program, it is an
  unrepresentable one.
- **Expected:** either termination, or a diagnostic once a value exceeds some
  documented magnitude.
- **Cause:** `Roman` is arbitrary-precision — `tiers: Vec<Tier>`
  (`roman.rs:6-9`) — so nothing ever overflows. `mag_mul` (`roman.rs:94`) is a
  doubling multiply, super-quadratic in the operand length, and `display`
  (`roman.rs:298`) walks every tier again. The cost is in the representation,
  not in a bug.

### D-21 · `mag_divmod`'s zero guard is a `debug_assert`

- **Severity:** low — unreachable today, and a latent release-only hang if any
  future caller stops guarding
- **Repro:** none reachable from source. Recorded for the invariant, not for a
  test.
- **Covered by:** this register only.
- **Observed:** every caller guards. `interp.rs:317` and `interp.rs:330` reject
  a zero divisor with `divisio per nullum` / `modulus per nullum` before
  reaching `div_rem`; `fraction::div` (`fraction.rs:31`) returns `None` on a
  zero divisor; `fraction::from_rational` and `fraction::mul` divide only by a
  constant grain; `exit_status` divides only by 256.

  A zero *denominator* in a fraction literal also never reaches a division, but
  **not** by the route first recorded here. The probes `°I:I/N`, `°I:I/` and
  `°I:I/O` all fail with `numerus Romanus vacuus` or
  `numerus Romanus invalidus`, which is `convert_single` (`roman.rs:193` and
  `roman.rs:205`). None of them reaches `roman.rs:252`'s `den.is_zero()` check.
  The conclusion holds — nothing divides — but the guard doing the work is
  `convert_single`, not `denominator est nullus`.
- **Also worth knowing: `roman.rs:253` looks like dead code.** For
  `den.is_zero()` to be true, `convert_int_roman` would have to return zero, and
  it appears it cannot: `convert_single` was evaluated over all 960,799 strings
  of length 1..7 over `I V X L C D M` and returned neither zero nor a negative
  (minimum 1). `convert_int_roman` then only multiplies and adds those, so its
  result is always ≥ 1. The one test that looks like it covers the branch,
  `roman.rs:446::parse_rejects_malformed_or_zero_fraction`, asserts only
  `is_err()`; run directly, `parse_roman("°V:I/nullus")` returns
  `Err("numerus Romanus invalidus: 'nullus'")`, so it passes through
  `roman.rs:205` and never exercises `roman.rs:253`. If the catalogue ratchet
  (design §7) classifies this site, `DEAD` is the honest label.
- **Expected:** a real guard, since `Roman::div_rem` (`roman.rs:336`) is `pub`.
- **Cause:** `roman.rs:110` —
  `debug_assert!(!d.is_empty(), "mag_divmod requires a non-zero divisor")`,
  compiled out in release. With `d` empty, `mag_cmp(n, d)` is `Greater`, so the
  early return is skipped and the doubling loop at `roman.rs:118` computes
  `mag_add(&dd, &dd)` on an empty `dd` forever, doubling `pow` until memory runs
  out.

### D-22 · The library interpolates English OS error strings into Latin diagnostics

- **Severity:** low — but it breaks the one rule the language has, and unlike
  D-11 it does so from the library, so every embedder inherits it
- **Repro:** three, all through `program::load_dir`. Not fixture-shaped: each
  needs a file mode or a byte sequence the corpus cannot carry in git, so they
  need a subprocess and a filesystem manipulation at test time.
- **Covered by:** `crates/lingua-serpentis/tests/cli.rs` (forthcoming — Task 9)
  and the `robustness.rs` `Latin only` invariant with a D-22 allowlist entry.
- **Observed:** measured 2026-08-03, each exiting 1 with empty stdout.
  - a non-UTF-8 `.liss` file in a program folder →
    `Error: scida 'principale.liss' legi non potest: stream did not contain valid UTF-8`
  - a `.liss` file with mode 000 →
    `Error: scida 'principale.liss' legi non potest: Permission denied (os error 13)`
  - a subdirectory with mode 000 →
    `Error: directorium '<absolute path>' legi non potest: Permission denied (os error 13)`

  The frame of each is correct Latin; the tail is `std::io::Error`'s English
  `Display`. The third also leaks an absolute filesystem path where every other
  diagnostic in the language uses a path relative to the program root.
- **Expected:** Latin throughout — the failure classified into a small set of
  Latin causes (not found, not readable, not valid UTF-8) rather than the OS
  string passed through.
- **Cause:** three sites, all in `program::collect_liss`, all the same shape
  `format!("… legi non potest: {}", e)`:
  - `program.rs:73` — `read_dir` failure, `directorium '{}' legi non potest: {}`
  - `program.rs:76` — directory-entry failure, `directorium legi non potest: {}`
  - `program.rs:84` — `read_to_string` failure, `scida '{}' legi non potest: {}`
- **Distinct from D-11.** D-11 is English *written by hand* in `main.rs`
  (`main.rs:24`, `main.rs:29`) and is fixed by translating two string literals.
  D-22 is the *library* interpolating a foreign string it did not author, and is
  fixed by classifying the error instead of forwarding it. Different code,
  different owner, different fix.
- **Note for Task 10 — do not weaken the rule to get green.** The robustness
  invariant's condition 6 ("the message contains no English") will fire on all
  three of these messages for any input the fuzzer generates that touches an
  unreadable or non-UTF-8 file. The correct response is an allowlist entry keyed
  to **D-22**, exactly as the design's §5 prescribes for D-02, D-11 and D-12, so
  that the exception disappears when the defect is fixed. Relaxing the denylist,
  or narrowing condition 6 to exclude library-originated messages, would hide
  this defect permanently and is the wrong move.

### D-23 · The Latin identifier checker is quadratic in name length

- **Severity:** low — reachable only with an unusually long identifier, but the
  slowdown is severe and undiagnosed
- **Repro:** `conformance`-external; `crates/lingua-serpentis/tests/robustness.rs`'s
  `nomen longissimum` pathology: a single top-level `ni` declaration whose name
  is 100,000 `a` characters. Not fixture-shaped: the fixture runner has no
  timeout, and the point being demonstrated is that the run exceeds one.
- **Covered by:** `robustness.rs`'s `terminates` invariant (per-input timeout,
  already allowlisted via D-20) with a D-23 allowlist entry in `pathologies()`.
- **Observed:** timed directly against `target/debug/lingua-serpentis` on
  2026-08-03 with an otherwise-trivial program (`munus initium reddit ni { ni
  <name> = °I; redde nullus; }`), name length vs. wall time: 1,000 → 0.31s;
  5,000 → 0.37s; 10,000 → 0.55s; 20,000 → 1.26s; 50,000 → 6.21s; 100,000 →
  24.0s. The run does terminate (exit 0, a `Monitum … fortasse non Latinum est`
  warning) — it is not a hang — but it blows through `robustness.rs`'s 10-second
  per-input deadline somewhere between 50,000 and 100,000 characters, and the
  growth curve (roughly doubling the input roughly quadruples the time from
  20,000 characters on) is quadratic, not linear.
- **Expected:** near-linear time in identifier length, or a length cap with a
  diagnostic.
- **Cause:** `crates/latinitas/src/analyze.rs:31-40` — `analyze`'s loop
  `for i in 0..=w.len() { let (stem, ending) = (&w[..i], &w[i..]); let Some(groups)
  = tables.stems.get(stem) else { continue }; ... }` hashes a `&w[..i]` slice
  against a `HashMap<String, _>` on every one of the `w.len() + 1` iterations.
  Hashing a slice is itself `O(i)`, so the total cost is `O(1 + 2 + … + n)` =
  `O(n²)` in the identifier's length. `latinity.rs:44`'s `check_name` calls
  `latinitas::is_latin` once per declaration site, so this is reachable from
  any single sufficiently long `ni`/`voc`/`munus`/parameter name — no repeated
  use or loop needed.
- **Distinct from D-20.** D-20 is exponential blow-up in `Roman`'s
  representation from repeated squaring in `roman.rs`; this is quadratic
  blow-up in a `HashMap` lookup loop in `latinitas`, triggered by a single
  identifier's length. They share the `terminates` rule because both are
  "eventually finishes, but not within a reasonable bound," not because they
  share a mechanism.

**§8.1 has since been corrected** (commit `6f5d6c9`), so the design and this
register now agree; the table above is the record of what was changed and why,
not a live disagreement. Two notes on that correction:

- **D-10.** The design's 116 was not wrong, it was attached to the wrong
  literal: `°C.C.C` does exit 116. That numeral is **10,100**, not 1,000,000 —
  `convert_int_roman` (`roman.rs:212`) splits on `.` and multiplies *pairwise*,
  adding an odd trailing term, so `C·C + C` = 10,100, which `scribe` confirms by
  printing `X̅C`. 10,100 mod 256 = 116. D-10's entry above stays stated against
  `°CCC` → 44, which is the clearer demonstration.
- **D-05.** The corrected §8.1 row records the boundary as lying between 1000
  and 2000, which is what was measured. It was not narrowed further; a
  robustness sweep should treat 2000 as the known-bad point, not as the exact
  limit.

Two smaller readings differ:

- **D-07** — §8 cites `interp.rs:165` for the `Flow::Return` match; it is
  `interp.rs:166`. `checker.rs:449` is exact.
- **D-11** — §8.1 says the *second* English message is wrong for a nonexistent
  directory argument. Measured, it is the *first* (`Error: file must have .liss
  extension`) that a nonexistent plain directory hits. The second misfires on a
  nonexistent `x.liss/` directory. Both are wrong; the entry records both.
